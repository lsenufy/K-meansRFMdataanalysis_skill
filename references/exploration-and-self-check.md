# 合理探索与至少三轮自检

## 1. 探索的自主性与范围

主流程是完成治理、RFM、K-means、基准、交叉与落地所需的可复用方法，Agent继续独立判断，不能只机械套阈值或固定步骤。可以主动发现问题、提出方法调整和有理由的补充；新增专题或改变已约定方案，先询问用户、确认后实施。

提案先完成必要的已授权盘点，使用户能够审阅：发现／依据、建议工作、预期信息价值、改变的口径或产物、工作范围与取舍。不要因等待确认而停止独立的已授权主线，也不要把沉默当批准。已批准的工作不重复询问。

探索围绕RFM与K-means及其业务使用，例如：

- 高频集中／并列值是否需要不同分档；低频大额与高频小额是否值得分开。
- 窗口长度、客户资历、季节性是否改变画像或行动优先级。
- 极端值是合法大客户、退款冲销还是质量问题；不同处理对结论的影响。
- 不同变换、标准化与竞争K是否带来稳定且可行动的区分。
- 有足够样本的交叉组是否提供额外经营信息，资源情景有何取舍。

这些是可能的问题，不要求每份数据都探索全部内容。不要为找“更好结果”无限搜索，或增加本范围之外的预测模型／工程部署。

## 2. 与主结果隔离

建议任务目录：

```text
analysis_run/
  main/                         固定口径下的主结果
  exploration/<topic>/          独立探索代码、参数与观察
  verification/<revision>/      最终三轮自检与复核
```

名称可以按项目适配，但探索必须单独建文件夹，不覆盖主结果。探索记录至少写清问题、依据、授权／确认、使用的输入／客户／窗口、与主方案的差异、结果、解释边界与是否提议提升为主方案。

原始输入共享只读。要采用新方案时，说明结果、版本、更改原因及影响并取得用户确认，再重新生成受影响结果和自检。未来结果被用于选择方案时标为事后探索；同一未来窗口不能再次当作未见数据证明新方案独立提升。

## 3. 自检不是形式计数

最终分析与结论初稿完成后依次进行至少三轮，各轮承担不同核查目标。每轮要实际检查数据和计算，写出证据及结论；仅列清单、重复同一输出或把“没有异常日志”当通过均不够。

| 轮次 | 重点 | 主要证据 |
|---|---|---|
| 1 数据 | 来源与版本、字段／状态语义、主键、过滤、窗口、资格与R/F/M重算 | 输入哈希、质量记录、独立重算、明细抽样与金额／次数对账 |
| 2 方法 | 得分方向／覆盖、Shopify逻辑、K的三项诊断、变换范围、未来隔离、策略冻结及方案调整授权 | 条件边界、候选与ARI明细、参数／代码、数据使用范围、变更确认 |
| 3 结果与交付 | 汇总、分母、基准、交叉、未来网格、报告数字与结论 | 客户表重汇总、等人数名单、溯源声明、图表／报告、复现路径 |

检查应与实际使用的方法对应。没有未来窗口时标为不适用，不凭空要求未来交易；缺少可自动证明的业务语义时标review，进一步读取源定义、抽样或独立复算后解释。

## 4. 自动自检命令

对本技能`run_segmentation.py`的结果：

```bash
python scripts/self_check.py --run outputs/demo --output verification/demo_v1 --claims examples/numeric_claims.example.json
```

`--run`指已有计算目录；`--output`是新的独立检查目录，不能覆盖原分析。路径按当前工作目录解释。`--claims`可选，示例声明仅适用于仓库的合成示例。自有数据和报告需要用自己的真实声明，不能照搬示例期望值。

检查记录包括：

- `round_1_data.json`
- `round_2_methods.json`
- `round_3_results.json`
- `summary.json`与`summary.md`

每项保存pass／fail／review状态、证据、适用的expected／actual／差异。记录输入和运行产物指纹，使通过记录对应到具体版本。若选K未完成、证据不足或业务语义无法自动判定，不能把中间状态包装为最终验收通过。

自动核验可能复用输入解析／治理，但应独立重算主要汇总与指标；共享部分的错误仍需要语义复核或另用SQL／手工样本检查。使用其他实现时，按三轮目标生成等价证据，不强制转换为本脚本格式。

## 5. 报告数字声明

`--claims`接受声明列表或包含`claims`列表的JSON：

```json
{
  "claims": [
    {
      "id": "report.customer_count",
      "file": "customer_labels.csv",
      "filter": {},
      "column": "*",
      "aggregation": "count",
      "expected": 24,
      "tolerance": 0
    }
  ]
}
```

`file`只可引用run目录内部CSV；filter按字段等值筛选。sum／mean对指定数值列汇总；count统计非空列或column=`*`的行数；value要求筛选后恰好一行。每项记录源文件哈希、匹配行数、实际数值、期望值和差异。

`tolerance`只表示绝对容差；可选`relative_tolerance`独立设置、默认0，避免大额指标因比例容差掩盖金额差异。按实际指标精度设置，不能为通过检查而放宽。声明应来自报告实际数字，覆盖影响业务结论的关键人数、贡献、对照与比率。没有声明时，报告数字完整性不能自动视作已核验。

## 6. Review闭环与修复

机器检查通过不代表语义、外部来源真实性或因果解释已被证明。即使声明数字一致，也应复核：有效行为是否合理、客户资格是否偏置、分母／单位／窗口是否相同、策略能否事前执行、结论是否超出证据、建议动作是否只是待验证假设。

另写`review_resolutions.md`，逐项列review编号、复核方式、具体证据／文件与位置、判断、剩余不确定性和处理者。可由主助手独立复算，必要时请独立审阅者检查；如由同一助手复核应如实标识，不冒充外部审计。

fail项先修复数据适配、代码、指标或报告，再生成新版结果，在新检查目录完成三轮最终复查。保留问题与修复记录，不覆盖失败证据，不手工删除失败状态。新结果或新报告有变更时，旧指纹的通过不能为新版背书。

最终交付要求：三轮都有实际记录、未解决的fail为零、review有可追踪复核或明确的解释边界、主结果与报告属于核验版本。确实无法解决的事项如实呈现，不能宣称全部确定可信。
